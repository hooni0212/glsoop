## 1. 징후/트리거

- 병합 전 충돌 가능성이 보일 때
- 문서 동기화 전 품질게이트 실패가 반복될 때
- 릴리스 직전 `dev/main` 정리가 필요한 때

## 2. 즉시 조치

1. 현재 브랜치/작업트리 상태를 확인한다.
2. 병합 대상 브랜치의 ancestry와 충돌 가능성을 먼저 점검한다.
3. 문서 반영이 필요하면 품질게이트를 선행한다.

## 3. 원인 확인 절차

1. `git status --branch`로 로컬 상태 확인
2. `git merge-base`/`git merge-tree`로 충돌 후보 파악
3. `npm run check:quality`로 문서 품질 실패 원인 분리

## 4. 복구 절차

1. 링크/문서 표준 오류를 수정한다.
2. 병합은 가능한 `--ff-only`를 우선 사용한다.
3. 병합 완료 후 원격 브랜치와 로컬 브랜치를 정리한다.

## 5. 검증 항목

- [ ] 병합 후 `git status`가 clean 상태인지
- [ ] `main`/`dev`가 원격과 동기화되었는지
- [ ] 문서 품질게이트가 통과하는지
- [ ] Notion sync report에서 `error=0`인지

## 6. 롤백 절차

1. 원격 반영 전이면 로컬에서 병합 커밋 범위를 점검 후 재실행한다.
2. 원격 반영 후 문제가 확인되면 hotfix 브랜치에서 역수정 문서/코드를 준비한다.
3. Notion 동기화는 수정 반영 후 다시 `dry-run -> push`로 재실행한다.

## 7. 커뮤니케이션 포인트

- 작업 시작: 범위/대상 브랜치 공유
- 병합 직전: 충돌 여부/리스크 공유
- 반영 완료: 커밋 범위, 검증 결과, 다음 액션 공유

## 8. FAQ

Q. 왜 `--ff-only`를 우선하나요?  
A. 이력을 선형으로 유지해 추적과 복구를 단순화하기 위해서다.

Q. 문서는 왜 품질게이트를 먼저 통과해야 하나요?  
A. 깨진 참조 상태로 Notion에 반영하면 검색/참조 신뢰도가 떨어진다.

## 9. editor2 Draft 운영 규칙 (2026-03-04)

1. 키 규칙
- Create: `glsoop:editor2:draft:create:u:{userIdOrAnon}`
- Edit: `glsoop:editor2:draft:edit:{postId}:u:{userIdOrAnon}`

2. 삭제 라이프사이클
- Create draft: 최초 `POST /api/posts` 성공 직후 즉시 삭제
- Edit draft: `PUT /api/posts/:id` 성공 후 baseline과 일치하면 삭제
- 수동 삭제: editor2의 `초안 삭제` 버튼 클릭 시 즉시 삭제
- 계정 충돌 방지: 현재 사용자 토큰과 다른 draft는 복구하지 않고 진입 시 삭제
- 만료 정리: 30일 초과 draft는 editor2 진입 시 자동 정리

3. 운영 원칙
- draft는 브라우저 localStorage 전용이며 서버 draft API를 추가하지 않는다.
- `posts.layout_json`은 optional 유지, `NULL`이면 legacy auto preset 렌더를 그대로 사용한다.

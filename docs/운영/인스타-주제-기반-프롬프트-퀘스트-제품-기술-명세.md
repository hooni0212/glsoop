## 1. 목적

인스타그램 게시 주제와 글숲 안의 글쓰기 행동을 연결한다.

예를 들어 인스타그램에 `지나간 연인에게 편지를 써봐요` 같은 게시글을 올리면, 글숲 운영자는 같은 주제를 퀘스트로 등록한다. 사용자는 성장 탭의 퀘스트에서 해당 주제를 보고 바로 글쓰기를 시작하며, 그 흐름으로 글을 발행하면 퀘스트가 완료된다.

v1 목표는 자동 인스타 연동이 아니라 운영자가 직접 입력하는 안정적인 운영 흐름이다.

---

## 2. v1 결정 사항

- 운영 방식: 관리자 수동 등록.
- 완료 방식: 프롬프트 선택 기반 자동 완료.
- 판정 기준: 사용자가 퀘스트 CTA에서 글쓰기를 시작하고, 해당 `quest_context`로 새 글을 발행하면 완료.
- 제외 범위:
  - 인스타 API 자동 연동.
  - 해시태그만으로 완료 처리.
  - AI/키워드 기반 내용 적합성 판정.
  - 운영자 수동 승인 완료.
- 기존 퀘스트/업적 조건은 그대로 유지한다.

## 3. 사용자 흐름

### 3.1 퀘스트 발견

모바일 성장 > 퀘스트 화면에서 프롬프트형 퀘스트를 일반 퀘스트보다 더 글쓰기 중심으로 보여준다.

표시 정보:

- 퀘스트 제목: 예 `지나간 연인에게 편지를 써봐요`
- 설명/본문 가이드: 예 `보내지 못한 말, 남겨둔 마음, 지금의 나에게 남은 것을 편지처럼 써보세요.`
- 보상 XP
- 진행 상태
- CTA: 기본 `이 주제로 글쓰기`

### 3.2 글쓰기 진입

사용자가 CTA를 누르면 모바일은 `/write`로 이동하면서 아래 문맥을 전달한다.

- `questStateId`
- `promptKey`

글쓰기 화면은 프롬프트 배너를 보여주고, 운영자가 지정한 기본 카테고리와 추천 해시태그를 적용한다.

원칙:

- 본문을 자동으로 채우지 않는다.
- 사용자가 직접 제목/본문을 입력해야 한다.
- 임시저장 시에도 퀘스트 문맥을 보존한다.
- 기존 일반 글쓰기 진입은 바뀌지 않는다.

### 3.3 발행/완료

사용자가 글을 발행하면 `POST /api/posts`에 선택 필드 `quest_context`를 함께 보낸다.

서버가 문맥을 검증하고 글 저장에 성공하면, 해당 퀘스트 진행도를 갱신한다.

완료 시 모바일은 발행 성공 화면 또는 토스트에서 `퀘스트 완료`를 알려주고, 보상 수령은 기존 퀘스트 보상 수령 흐름을 사용한다.

## 4. 관리자 운영 흐름

### 4.1 프롬프트 퀘스트 템플릿 등록

관리자 > 퀘스트 템플릿에서 `프롬프트 글쓰기 퀘스트` 유형을 선택할 수 있게 한다.

운영자가 입력하는 필드:

- 제목
- 설명
- 프롬프트 키
- 프롬프트 본문 가이드
- CTA 문구
- 기본 카테고리
- 추천 해시태그
- 출처 메모: 예 `instagram`
- 인스타 게시물 URL 또는 운영 메모
- 목표값: v1 기본 `1`
- 보상 XP

프롬프트 키는 사람이 읽을 수 있는 안정 키를 권장한다.

예:

```text
letter_to_past_love_202605
```

### 4.2 캠페인 연결

운영자는 기존 캠페인 관리에서 해당 템플릿을 이벤트/시즌/위클리 캠페인에 연결한다.

권장 운영 방식:

- 인스타 게시 일정과 같은 시작일/종료일을 둔다.
- 캠페인이 활성화되기 전에 최소 1개 템플릿이 연결되어 있어야 한다.
- 활성 캠페인이 비어 있으면 기존 성장 운영 알림/헬스 체크에서 확인한다.

## 5. 데이터 모델

### 5.1 `quest_templates`

기존 테이블을 유지하고 새 조건 타입을 추가한다.

```text
condition_type = 'PROMPT_POST_CREATED'
target_value = 1
template_kind = 'quest'
ui_json = JSON string
```

`ui_json` 예시:

```json
{
  "quest_kind": "writing_prompt",
  "prompt": {
    "key": "letter_to_past_love_202605",
    "title": "지나간 연인에게 편지를 써봐요",
    "body": "보내지 못한 말, 남겨둔 마음, 지금의 나에게 남은 것을 편지처럼 써보세요.",
    "cta_label": "이 주제로 글쓰기",
    "default_category": "essay",
    "suggested_hashtags": ["편지", "지난사랑", "글감"],
    "source": "instagram",
    "source_url": "https://instagram.com/..."
  }
}
```

### 5.2 신규 추적 테이블

프롬프트 퀘스트 완료 근거를 게시글과 분리해 보관한다.

권장 테이블명:

```text
quest_post_submissions
```

권장 컬럼:

- `id`
- `user_id`
- `post_id`
- `state_id`
- `campaign_id`
- `template_id`
- `prompt_key`
- `created_at`

권장 제약:

- `post_id`는 `posts.id`를 참조하고 글 삭제 시 함께 삭제한다.
- `state_id`는 `user_quest_state.id`를 참조한다.
- 같은 글이 같은 퀘스트에 중복 제출되지 않도록 `UNIQUE(state_id, post_id)`를 둔다.
- v1은 목표값 1을 기본으로 하지만, 진행도 계산은 제출 row 수 기준으로 확장 가능하게 둔다.

## 6. API 계약

### 6.1 활성 퀘스트 조회

기존 `GET /api/quests/active`와 `GET /api/growth/dashboard` 응답을 유지한다.

서버는 `ui_json` 문자열을 계속 내려준다. 모바일은 `ui_json`을 파싱해서 `quest_kind === "writing_prompt"`이면 프롬프트 UI를 렌더링한다.

하위 호환 원칙:

- 새 필드를 모르는 클라이언트는 일반 퀘스트처럼 표시해도 된다.
- 기존 조건 타입의 진행도 계산은 바꾸지 않는다.

### 6.2 게시글 작성

`POST /api/posts` 요청에 선택 필드를 추가한다.

```json
{
  "title": "보내지 못한 편지",
  "content": "그때는 말하지 못했지만...",
  "category": "essay",
  "hashtags": ["편지", "지난사랑"],
  "quest_context": {
    "state_id": 123,
    "prompt_key": "letter_to_past_love_202605"
  }
}
```

성공 응답은 기존 응답을 유지하고, 퀘스트 문맥이 처리된 경우 `quest_completion`을 추가한다.

```json
{
  "ok": true,
  "message": "글이 저장되었습니다.",
  "post_id": 456,
  "quest_completion": {
    "state_id": 123,
    "template_id": 77,
    "campaign_id": 12,
    "prompt_key": "letter_to_past_love_202605",
    "progress": 1,
    "target": 1,
    "status": "completed",
    "completed_at": "2026-05-02T10:20:30.000Z"
  }
}
```

오류 원칙:

- `quest_context`가 없으면 기존 글쓰기와 동일하게 처리한다.
- `quest_context`가 있고 검증에 실패하면 글을 저장하지 않는다.
- 다른 사용자의 `state_id`는 `403`.
- 없는 `state_id`는 `404`.
- 조건 타입이 `PROMPT_POST_CREATED`가 아니거나 `prompt_key`가 맞지 않으면 `400`.
- 캠페인이 비활성/기간 외이면 `409`.

### 6.3 글 수정

`PUT /api/posts/:id`는 v1에서 퀘스트 진행도를 변경하지 않는다.

이유:

- 퀘스트는 새 글 작성 행동을 보상한다.
- 수정으로 프롬프트 완료를 뒤늦게 만들면 검증과 운영 설명이 복잡해진다.

## 7. 서버 처리 규칙

### 7.1 검증 순서

`POST /api/posts`에서 `quest_context`가 있으면 글 저장 전에 아래를 검증한다.

1. 로그인 사용자와 `user_quest_state.user_id`가 일치한다.
2. 연결된 템플릿의 `condition_type`이 `PROMPT_POST_CREATED`이다.
3. 템플릿이 활성 상태다.
4. 캠페인이 활성 상태이고 현재 시간이 기간 안에 있다.
5. `ui_json.prompt.key`와 요청 `prompt_key`가 일치한다.
6. 유료 권한 잠금이 있는 템플릿이면 사용자가 필요 권한을 가지고 있다.

### 7.2 저장/진행도 갱신

검증 후 하나의 트랜잭션으로 처리한다.

1. `posts` row 생성.
2. 해시태그 저장.
3. `quest_post_submissions` row 생성.
4. 해당 `state_id`의 제출 수를 기준으로 `user_quest_state.progress` 갱신.
5. `progress >= target_value`이면 `completed_at`을 최초 1회 기록.
6. 기존 성장/활동 이벤트 처리를 이어서 실행한다.

이미 완료된 퀘스트에 유효한 문맥으로 다시 글을 발행하는 경우:

- 글은 저장한다.
- 제출 row는 저장 가능하다.
- `completed_at`과 보상 상태는 중복 변경하지 않는다.
- 응답은 `quest_completion.status = "already_completed"`로 내려준다.

## 8. 모바일 변경 사항

### 8.1 퀘스트 화면

`GrowthQuest.uiJson`을 파싱해 프롬프트형 퀘스트를 감지한다.

프롬프트형 퀘스트 CTA 조건:

- 로그인 상태.
- `isLocked`가 false.
- `status !== "completed"`이거나 보상 미수령 안내를 별도로 표시.

CTA 동작:

```text
/write?questStateId={stateId}&promptKey={prompt.key}
```

### 8.2 글쓰기 화면

글쓰기 화면은 query param을 읽어 활성 퀘스트 목록에서 같은 `stateId`와 `promptKey`를 찾는다.

찾으면:

- 프롬프트 배너 표시.
- 기본 카테고리 선택.
- 추천 해시태그 입력.
- 제출 payload에 `quest_context` 포함.

찾지 못하면:

- 일반 글쓰기 화면으로 유지한다.
- 사용자가 퀘스트에서 들어왔는데 정보가 만료된 경우 토스트로 안내하고 일반 글쓰기를 계속 허용할 수 있다. 단, 서버에 잘못된 `quest_context`를 보내지 않는다.

### 8.3 임시저장

퀘스트 글쓰기에서 임시저장하면 draft에 아래를 보존한다.

- `questStateId`
- `promptKey`
- 프롬프트 제목/본문 스냅샷

draft 복구 시 서버의 현재 활성 퀘스트와 다시 대조한다. 더 이상 유효하지 않으면 일반 draft로 열고 퀘스트 완료 문맥은 제거한다.

## 9. 관리자 UI 변경 사항

기존 `UI 메타(JSON)` 직접 입력은 유지하되, 프롬프트형 퀘스트를 쉽게 만들 수 있는 입력 UI를 추가한다.

권장 UI:

- 조건 타입 선택에 `프롬프트 글쓰기` 추가.
- 선택 시 프롬프트 입력 필드 노출.
- 저장 시 서버로 `condition_type = PROMPT_POST_CREATED`와 `ui_json`을 함께 전송.
- JSON textarea는 고급 입력으로 접어두거나 자동 생성된 값을 보여준다.

검증:

- `prompt.key` 필수.
- `prompt.title` 필수.
- `target_value`는 v1에서 1 이상만 허용하되 운영 기본값은 1.
- `default_category`는 서버가 허용하는 게시글 카테고리만 허용.

## 10. 테스트 체크포인트

### 10.1 서버

- 관리자 API로 `PROMPT_POST_CREATED` 템플릿 생성 가능.
- 활성 퀘스트 응답에 프롬프트 `ui_json`이 보존된다.
- 올바른 `quest_context`로 `POST /api/posts`를 호출하면 글 생성과 퀘스트 완료가 함께 처리된다.
- 잘못된 `state_id`, 다른 사용자 state, 잘못된 `prompt_key`, 기간 외 캠페인은 실패한다.
- `quest_context` 없는 일반 글쓰기는 기존과 동일하다.
- 이미 완료된 퀘스트에 다시 작성해도 보상/완료 시각이 중복 변경되지 않는다.

### 10.2 모바일

- 퀘스트 화면에서 프롬프트형 퀘스트에 CTA가 보인다.
- CTA로 글쓰기 진입 시 프롬프트 배너, 기본 카테고리, 추천 해시태그가 적용된다.
- 발행 payload에 `quest_context`가 포함된다.
- 발행 성공 후 퀘스트 완료 토스트 또는 완료 안내가 보인다.
- draft 복구 시 유효한 퀘스트 문맥은 유지되고, 만료된 문맥은 제거된다.

### 10.3 관리자

- 운영자가 JSON을 직접 몰라도 프롬프트 퀘스트를 만들 수 있다.
- 캠페인에 템플릿을 연결하고 활성화하면 모바일 활성 퀘스트에 노출된다.
- 활성 캠페인이 비어 있으면 기존 성장 운영 점검에서 경고가 유지된다.

## 11. 단계별 구현 순서

1. 서버 마이그레이션: `quest_post_submissions` 추가.
2. 서버 퀘스트 서비스: `PROMPT_POST_CREATED` 진행도 계산/갱신 경로 추가.
3. 서버 게시글 작성 API: `quest_context` 검증과 트랜잭션 저장 추가.
4. 관리자 API/UI: 프롬프트형 퀘스트 입력 지원.
5. 모바일 성장 퀘스트 화면: 프롬프트 카드/CTA 추가.
6. 모바일 글쓰기 화면: 프롬프트 문맥 표시, draft 보존, 발행 payload 추가.
7. 서버/모바일 E2E 추가.
8. API/DB 레퍼런스 문서에 실제 구현 계약 반영.

## 12. 운영 예시

인스타 게시 문구:

```text
지나간 연인에게 편지를 써봐요.
보내지 못한 말이 있다면 오늘 글숲에 남겨보세요.
```

관리자 입력:

- 제목: `지나간 연인에게 편지를 써봐요`

## 13. 미결정/후속 과제

- 인스타 게시물 URL을 필수로 둘지 선택값으로 둘지.
- 프롬프트 퀘스트를 홈/글쓰기 첫 화면에도 노출할지.
- 장기적으로 `writing_prompts` 전용 테이블을 둘지.
- 프롬프트 완료 후 활동함/푸시 알림까지 만들지.

v1에서는 위 항목을 모두 후속으로 두고, 관리자 입력 + 퀘스트 CTA + 글 발행 완료 처리만 구현한다.
